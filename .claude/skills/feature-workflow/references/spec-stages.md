# Stages 1 to 7: the specification

Each stage is written in English, in the feature's folder, from its template in `templates/`, and covers only what the feature adds (`docs/process/feature-stages.md`, section 3). The files and what each holds are in `docs/process/feature-stages.md`, section 1; what each stage answers is in its section 2. When there are earlier features, use the most complete one as the model of shape and depth; the first feature takes the templates' shape.

## For every stage

- **Start from the previous stage, accepted.** Read it, and read the same stage of the earlier features, so that you cite them instead of repeating them.
- **Open with the goal and the delta.** Say what the stage answers, and that the earlier features' stages still apply.
- **Cite the source of every rule** by id (`BRnn`, `UC-Pnn`, `DMPn`, `ADPn`), and cite earlier features by stage and section ("Feature 001, BR09").
- **Prefixed ids, never `G`.** From the second feature on, the ids that can be confused carry the feature's prefix (`docs/process/feature-stages.md`, section 3); `G` belongs to `docs/recommendations.md` alone.
- **End with the open decisions** the stage leaves to the next one, each with a recommendation. The user decides them; that is what acceptance is.
- **Record the acceptance in the document itself** when the user accepts: the date, and any answer that changes what was written. The feature's row in the index of `docs/features/README.md` is written once, when stage 1 opens, and its "State" column changes only at the milestones (stage 1 accepted, stage 8 approved, merged, in production); the history stays in the feature's folder. The `CLAUDE.md` files get no feature state.
- **Don't rewrite an earlier feature's stage.** A new decision that contradicts it is recorded in the new feature.
- **davna stands alone.** Every stage is written on davna's own terms. A need that comes from a project building on davna becomes a generic extension point, port or contract; no stage names such a project (`docs/process/feature-stages.md`, section 3).

## Stage 7 in particular

Stage 7 is where most go-live surprises are born, so check it against how the repository is really deployed (`docs/process/go-live.md`, sections 2 and 3):

- **The validation plan must be possible.** No merge into `main` deploys by itself today: the repository's CI (`.github/workflows/checks.yml`) only checks conformance and deploys nothing, the backend images are built and pulled on the server by hand, and `apps/client.app` runs on Vercel (`docs/recommendations.md`, RG14). The local `docker-compose.yml` (`yarn api:up`, `yarn api:down`) is the first place to try a real OpenAI call, the ffmpeg conversion inside the image or the GridFS storage, once its stale paths are fixed (RG03). What only production can show becomes checks right after the deploy, inside the "Turn on" steps.
- **The image comes first.** A feature that changes `apps/monolith.api`, `apps/multimedia.processing` (or `apps/interaction.conductor`, once it ships) plans its image built from the change's commit, started and healthy, with an immutable tag, before the go-live ([image before go-live](../../../../docs/patterns/image-before-go-live.md)).
- **Name the deploy window.** A change that is not additive (a renamed field, a removed route, a changed WebSocket event that `apps/client.app` relies on) breaks the running code until the new code is up. Say the order between the API images and the client deployment, and the window agreed with the user.
- **List the manual setup** the deploy needs (variables in the server's `.env` and in the Vercel project, keys at the providers, DNS, certificates, the image registry) and who does each part. This becomes the Prepare and Ship groups of the go-live list.
- **New configuration** goes into the package's configuration module, mandatory and with no production default ([configuration](../../../../docs/patterns/configuration.md)); a `NEXT_PUBLIC_*` value goes to the browser and is never a secret.
- **List the third-party assumptions** (OpenAI, Firebase, AWS S3, Google Sheets, Vercel), each with the way to check it (`docs/process/production-procedures.md`, section 4).
- **Say what is done after the deploy:** tightening a `$jsonSchema` validator once the documents comply, dropping a field or an index the old code used, retiring a manual procedure, deleting test records (`docs/process/feature-closing.md`, sections 2 and 3).
